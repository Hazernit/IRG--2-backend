# Умный реестр подписок

Backend-ядро для учёта подписок и регулярных платежей. API создаёт обязательства,
показывает ближайшие списания, ведёт историю оплат и уведомляет клиентов об
удалениях через Server-Sent Events (SSE).

## Стек

- Python 3.12, FastAPI, Pydantic;
- SQLAlchemy 2 (async) и PostgreSQL;
- Alembic;
- pytest;
- Docker Compose.

## Запуск

Нужны Docker и Docker Compose. Создавать `.env` для контейнерного запуска не
обязательно: безопасные локальные значения уже заданы в `docker-compose.yml`.

```bash
docker compose up --build
```

Контейнер API дождётся PostgreSQL, автоматически выполнит `alembic upgrade head`
и запустит приложение. После старта доступны:

- Swagger UI: <http://localhost:8000/docs>
- OpenAPI: <http://localhost:8000/openapi.json>
- проверка состояния: <http://localhost:8000/health>
- поток SSE: <http://localhost:8000/events>

Остановить проект:

```bash
docker compose down
```

Удалить также локальные данные PostgreSQL:

```bash
docker compose down -v
```

## Локальный запуск и тесты

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
pytest -q
```

Для локального запуска приложения без Docker задайте `DATABASE_URL`, примените
миграции и запустите Uvicorn:

```bash
export DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/subscriptions
alembic upgrade head
uvicorn app.main:app --reload
```

Тесты не подключаются к PostgreSQL и не вызывают внешние сервисы: репозиторий,
часы и брокер событий заменяются тестовыми реализациями.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/obligations` | Создать обязательство |
| `GET` | `/obligations` | Получить список с фильтрами `category` и `status` |
| `GET` | `/obligations/upcoming?days=7` | Ближайшие активные обязательства и суммы по валютам |
| `POST` | `/obligations/{id}/pay` | Зафиксировать оплату |
| `PATCH` | `/obligations/{id}/cancel` | Отменить активное обязательство |
| `DELETE` | `/obligations/{id}` | Удалить обязательство и историю оплат |
| `GET` | `/events` | Подписаться на SSE-события |

### Примеры запросов

Создание подписки:

```bash
curl -X POST http://localhost:8000/obligations \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Яндекс.Плюс",
    "amount": 399.00,
    "currency": "RUB",
    "category": "subscription",
    "recurrence": "monthly",
    "next_payment_date": "2026-07-20"
  }'
```

Одновременная фильтрация и получение ближайших списаний:

```bash
curl 'http://localhost:8000/obligations?category=subscription&status=active'
curl 'http://localhost:8000/obligations/upcoming?days=14'
```

Оплата, отмена и удаление:

```bash
curl -X POST http://localhost:8000/obligations/OBLIGATION_ID/pay
curl -X PATCH http://localhost:8000/obligations/OBLIGATION_ID/cancel
curl -i -X DELETE http://localhost:8000/obligations/OBLIGATION_ID
```

Просмотр событий удаления:

```bash
curl -N http://localhost:8000/events
```

Событие передаётся после успешного коммита удаления:

```text
event: obligation_deleted
data: {"type":"obligation_deleted","id":"..."}
```

## Бизнес-решения

### Lazy expiry

Перед `GET /obligations` одним запросом обновляются все активные разовые записи,
у которых `next_payment_date < today`. Они получают статус `expired`.

Рекуррентные обязательства не истекают автоматически: прошедшая дата означает,
что пользователь ещё не отметил очередную оплату, но сама подписка продолжает
действовать. Это также позволяет зафиксировать просроченную оплату через `/pay`.

При создании правило из задания применяется буквально: любая запись с датой в
прошлом сразу получает `expired`, в том числе рекуррентная.

### Календарная рекуррентность

Дата сдвигается от текущей плановой даты с помощью `dateutil.relativedelta`, а не
от момента нажатия «Оплачено». Поэтому поздняя оплата не переносит весь график.

Примеры:

- 31 января + месяц = 28 февраля (29 февраля в високосный год);
- 31 января + квартал = 30 апреля;
- 29 февраля + год = 28 февраля.

После сдвига 31 января на 28 февраля следующий сдвиг даст 28 марта. Чтобы всегда
восстанавливать исходный день месяца, модели понадобилось бы дополнительное поле
вроде `billing_day`; его нет в заданной структуре данных.

### Целостность операций

Оплата выполняется в одной транзакции. Обязательство читается с `FOR UPDATE`,
чтобы два параллельных запроса не создали две оплаты за один период. Платёж хранит
снимок суммы и валюты на момент операции. Удаление платежей обеспечено внешним
ключом `ON DELETE CASCADE`.

Сравнение дублей по названию не учитывает регистр. Уникального ограничения нет
намеренно: по требованиям дубль должен быть сохранён, а клиент получает warning.

`/obligations/upcoming` возвращает только активные записи. Отменённые и истёкшие
обязательства не являются предстоящими списаниями и не должны создавать alerts.
Диапазон дат включительный: `[today, today + days]`.

## Компромиссы и возможные улучшения

- SSE-брокер хранится в памяти процесса. Для нескольких экземпляров API нужен
  общий транспорт, например Redis Pub/Sub или PostgreSQL `LISTEN/NOTIFY`.
- В модели нет пользователя и авторизации: текущая версия представляет единый
  реестр. Для production нужны `user_id`, аутентификация и изоляция данных.
- Список пока без пагинации; она потребуется при росте истории.
- Поддерживаются валюты RUB, USD и EUR из задания. Для полного ISO 4217 лучше
  подключить справочник валют.
- Для абсолютно строгого обнаружения дублей при конкурентном создании можно
  использовать advisory lock по нормализованному названию. Уникальный индекс
  здесь неприменим, поскольку дубли разрешены.
- В production стоит добавить интеграционные тесты с временным PostgreSQL,
  метрики, трассировку и структурированные логи.

## Мотивация участия — черновик

Меня привлекает сочетание понятной пользовательской пользы и нетривиальных
backend-задач: календарной логики, консистентности платежей и надёжного API для
AI-агента. В AI-продукте я вижу свою роль в создании предсказуемого backend-ядра:
формализации бизнес-правил, стабильных контрактов и безопасной интеграции моделей
с пользовательскими данными.

Ответ о количестве часов в неделю и сроке участия необходимо заполнить лично
перед отправкой — это зависит от реальной доступности кандидата.
